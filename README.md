# 8ec.jp — 株式会社エイト コーポレートサイト

法人向け総合ITサービス「株式会社エイト」（[8ec.jp](https://8ec.jp/)）の静的サイトです。
これまで ZIP でやり取りしていたものを **git 管理下に整備** し、
リニューアル作業を差分・レビュー・履歴付きで進められるようにしています。
デプロイは **Vercel** に連動し、`main` への push で本番公開、PR ごとにプレビューURLが自動発行されます。

## 在庫データの更新（仕入先カタログ／旧トップの静的データ）

> トップページ（`/`）の商品表示は、2026-09 のリニューアルで `/zaiko` の実在庫
> （Supabase の公開ビュー `inv_public_catalog`）に切り替えました。下記の
> `assets/inventory-data.js` はトップからは読み込まなくなり、`/admin/catalog/` の
> 仕入先カタログ管理だけが使っています。

仕入先から届いた在庫Excelは、取り込みスクリプトで `assets/inventory-data.js` に反映します。
仕入先ごとに列の並びが違うので、読み取りルールは `tools/import-stock.py` に集約しています。

```bash
pip install openpyxl
python3 tools/import-stock.py <届いたxlsx> [<xlsx> ...]
```

- 対応フォーマット：SB C&S（HPEサーバー・ストレージ）／BUFFALO NW製品／LES PCStock（レノボ）／エレコム
- 同じ型番が既にあれば、**在庫・価格・更新日だけ**を上書きします
- 商品画像・メーカーページURL・カテゴリ分類は、手で整えた内容を残します
- 新しい仕入先が増えたときは `READERS` に読み取り関数を1つ足してください

### CSVで書き出す

仕入先に画像や見積もりを依頼するときの型番リスト、社内での内容確認に使えます。
Excelでそのまま開けるよう、BOM付きUTF-8・CRLF で出力します。

```bash
python3 tools/export-csv.py                 # 在庫一覧_YYYY-MM-DD.csv を作る
python3 tools/export-csv.py /path/out.csv   # 出力先を指定する
```

商品画像の有無も列に入るので、どの型番の画像が足りていないかがそのまま分かります。

## 商品画像（旧トップ・仕入先カタログ向け）

> いまの公開ページ（`/` と `/zaiko` 連動の商品カード）の写真は、上の
> 「商品写真は楽天から取り込む」の経路です。ここから下は、`/admin/catalog/` の
> 仕入先カタログ（`assets/product-images.json`）についての説明です。

実写があるものはそれを、無いものは `assets/product-art.js` が型番とカテゴリから機器の種類を
判定して描いたイラストを表示します。イラストには **「イメージ図」** と明示しているので、
実物の写真だと誤解されることはありません。

型番と画像の対応は `assets/product-images.json` に持ちます。在庫データとは別ファイルなので、
在庫を更新しても画像は消えません。

```bash
python3 tools/import-images.py --status      # 型番ごとの画像の有無を集計
```

### 画像を増やす

**型番から画像を自動検索する方式は採っていません。** 楽天・Yahoo!の商品APIはJANコードで
画像を返せますが、あれは他の小売店が撮影した写真で、自社の商用サイトに転載すると
著作権侵害になります。メーカーサイトの画像を直リンクするのも、相手の帯域を無断で使ううえ、
URLが変わると静かに壊れます。

使えるのは、**メーカーまたは仕入先から販売目的での利用を許諾された画像**だけです。
入手経路は主に2つで、どちらも取り込みツールが対応しています。

**1. 仕入先の商品マスタ（型番列と画像URL列を持つCSV / Excel）**

SB C&S・ダイワボウ情報システムなどが販売店向けに配布しているものです。
在庫表と同じ窓口で「画像URL付きの商品マスタ」を依頼すれば入手できます。

```bash
python3 tools/import-images.py --from-file 商品マスタ.xlsx \
    --model-col 型番 --url-col 画像URL --credit エレコム --download
```

**2. メーカーの販売店向け画像ダウンロード（型番名の画像ファイルが入ったフォルダ）**

エレコム・バッファロー・アイ・オー・データなどが、販売店アカウント向けに配布しています。

```bash
python3 tools/import-images.py --from-dir ~/Downloads/elecom-images --credit エレコム
```

**3. 手元でコピーしたURLを貼り付ける**

自社ショップの管理画面やメーカーの製品ページからコピーしたURLを、そのまま流し込めます。
区切りはタブ・カンマ・空白のいずれでも構いません。

```bash
python3 tools/import-images.py --paste --credit 自社撮影
# 型番<タブ>URL を1行ずつ貼り付けて Ctrl-D
```

**4. 自社ショップ（`/shop`）から型番一致で取り込む**

ショップは Supabase の `shop_products` ビューを見ており、`model`（型番）と画像URLが
同じ行にあります。そのため手で貼らなくても型番で自動照合できます。

```bash
python3 tools/import-images.py --from-shop          # 一致する型番を一覧表示するだけ
python3 tools/import-images.py --from-shop --yes    # 実際に取り込む
```

> **注意：** ショップはオークション仕入れの**中古品を1点ずつ**扱っており、写真はその個体を
> 撮ったものです。新品として掲載する法人在庫にそのまま流用すると、実物と食い違います
> （傷のある中古機の写真が「新品・在庫275点」の隣に出るなど）。著作権の問題はありませんが、
> 表示としての正確さの問題があるため、`--from-shop` は一覧を出すだけで止まり、
> 取り込むには `--yes` を明示する必要があります。

**5. 管理画面から登録する（`/admin/catalog/`）← 日常運用はこれ**

事務の共有アカウントでログインし、商品ごとに画像URLを入力します。
保存すると **デプロイを待たずにサイトへ反映** されます（Supabase の `catalog_images` に保存）。

- 型番・商品名・商品コード・メーカーで検索、画像の状態（未登録／準備中／画像あり）で絞り込み
- 「まとめて貼り付け」で、ExcelやCSVから2列（商品コード＋URL）をそのまま流し込める
- 「アップ」ボタンで画像ファイルを直接アップロード（Supabase Storage に入り、URLが自動で入る）
- 「JSON書き出し」で `assets/product-images.json` に反映する形でも取り出せる

初回のみ `admin/catalog/supabase-setup.sql` を Supabase の SQL Editor で実行してください。

**6. 自社で画像を用意する（`images/products/` 配信）**

商品コードでファイル名を固定し、自社ドメインから配信する方式です。
URLが `https://8ec.jp/images/products/<商品コード>.webp` で固定されるため、
正式な画像を同じファイル名で上書きすれば、データを触らずに差し替わります。

```bash
python3 tools/import-images.py --from-manifest assets/product-image-manifest.csv
```

マニフェストの「状態」列が「準備中」「差替待ち」のものは `placeholder` として登録され、
**サイト上ではイラスト表示のまま**になります。「商品画像準備中」の画像より、
機器の種類が分かるイラストの方が一覧で役に立つためです。
準備中の画像もそのまま出したい場合は `--show-placeholders` を付けてください。

`--download` を付けると画像を `assets/products/` に保存し、そちらを参照します。
直リンクを避けられるので、本番ではこちらを推奨します
（外部へ接続できる環境で実行してください）。

## デプロイ（git 連動 / Vercel）

GitHub リポジトリ `morishin1/8ec` を Vercel プロジェクト **8ec** に接続しています。

| きっかけ | 結果 |
|---|---|
| `main` へ push / マージ | **本番デプロイ**（https://8ec.vercel.app/ 、将来は 8ec.jp） |
| PR を作成 / 更新 | その差分の **プレビューURL** が PR に自動投稿される |

ビルドは不要（静的サイト）。`.vercelignore` で `archive/`・`notion-proxy/` 等は配信されません。

### Vercel 初回接続（1回のみ）

Vercel の `8ec` プロジェクト → **Settings → Git** →
**Connect Git Repository** で `morishin1/8ec` を接続し、Production Branch を `main` に設定します。
ビルド設定は次のとおり（静的サイト）:

- **Framework Preset**: Other
- **Build Command**: なし（空欄）
- **Output Directory**: 既定（リポジトリ直下）

### リニューアルの進め方（推奨フロー）

1. 作業用ブランチを切る（例: `git switch -c feature/top-renewal`）
2. HTML/CSS/JS を編集してコミット → PR を作成
3. PR に付く **プレビューURL** で仕上がりを確認・レビュー
4. `main` にマージ → 本番へ自動反映

### 本番 8ec.jp への切り替え

Vercel プロジェクトの **Settings → Domains** で `8ec.jp` を追加し、
表示される DNS レコード（A / CNAME）を 8ec.jp のネームサーバー側に設定すれば、
本番ドメインが Vercel の配信に切り替わります。

## 備品在庫管理（/zaiko/）

社内のPC・IT機器・備品・消耗品を、**スマホの標準カメラでQRを読むだけ**で管理します。

```
スマホ標準カメラ → QR読取 → その商品のページ → 入庫・出庫・貸出・返却・移動・棚卸
```

### QRにはURLだけを入れる

QRコードに商品情報は持たせません。入っているのはURLだけで、中身は常にその場でサーバーから取ります。
ラベルを貼り替えずに商品名も置き場所も変えられます。

| 対象 | URL |
|---|---|
| 個体（1台ずつ） | `https://www.8ec.jp/zaiko/items/PC-00125` |
| 数量品 | `https://www.8ec.jp/zaiko/products/SKU-0001` |
| 保管場所（棚QR） | `https://www.8ec.jp/zaiko/locations/L3` |

このURLで**そのページが直接開く**ことが最優先の要件なので、`vercel.json` に書き戻し（rewrite）を入れて
`/zaiko/items/…` を `/zaiko/index.html` に渡し、画面側でパスを見て表示を決めています。
実ファイル（`app.js` など）があればそちらが優先されるので、書き戻しには巻き込まれません。
未ログインでQRを読んだ場合は、ログイン後にそのページへ戻します。

読取から操作完了までは **2〜3タップ**です（詳細 → 操作ボタン → 確定）。
QRのURLで開いたときは、まずその1件だけを取りに行って先に描き、一覧用のデータは後から裏で読み込みます。

### 販売側の在庫との違い

| | `/zaiko/`（社内の備品） | `/admin/`（中古の販売） | `/admin/ec/`（新品の販売） |
|---|---|---|---|
| 目的 | 社内で使う機器・消耗品 | オークション仕入れの中古を売る | モールに新品を出す |
| 動き | 貸出・返却・移動・棚卸 | 仕入 → 出品 → 販売 | 出品 → 在庫連動 |
| 表 | `inventory_*` | `ec_items` | `ec_products` |

3つとも表が別なので、互いに影響しません。

### セットアップ

Supabase の SQL Editor で `zaiko/setup.sql` を実行します。何度実行しても安全です。
カテゴリと保管場所（本社・柏・岩瀬）は最初から入っているので、そのまま登録を始められます。

本番は `setup.sql` 全体を再実行しない運用なので、差分だけを当てるファイルを
`zaiko/migrations/` に置いています（上から順に実行。いずれも何度実行しても安全です）。

| ファイル | 中身 |
|---|---|
| `2026-09-18-channel-listings-split.sql` | 商品×チャネルの掲載情報を `inventory_channel_listings` に分離 |
| `2026-09-18-rakuten-external-item-code.sql` | 楽天の `itemCode` を内部SKUと分ける列 |
| `2026-09-19-public-catalog.sql` | 8RENT・商品画像・楽天連携の関数と、公開ビュー `inv_public_catalog` |
| `2026-09-19-rental-sale-channels.sql` | 楽天＝販売／8EC＝レンタルの整理（公開条件を `rental_enabled` だけにし、掲載と販売可能数量を分ける） |
| `2026-09-19-item-rental-eligible.sql` | 個体単位のレンタル対象 `inventory_items.rental_eligible` と、在庫一覧のまとめて操作 `inv_items_bulk_op()`。**実行直後はどの個体もレンタル対象ではないので、8ECのレンタル可能数は0になります**（在庫一覧で「8RENTに出す」個体を選んでください） |
| `2026-09-19-rakuten-image-sync.sql` | 楽天の商品画像を `inventory_products.images` へ同期（`inv_rakuten_sync_targets()` を追加、同期は `image_url` を触らない）。あわせて `supabase functions deploy rakuten-product-sync` が必要 |
| `2026-09-19-listings-from-items.sql` | 個体別の出品情報（`inventory_channels`）から、商品単位の楽天listingを補完。**同じ商品ページに複数台をぶら下げている商品が、画像同期の対象から漏れていたのを直します** |
| `2026-09-19-rental-by-condition.sql` | 8RENTのレンタルを「個体在庫」から**条件で選ぶ商品**へ。メーカー＋型番で1機種にまとめる `inv_model_key()`、在庫0でも申込を受ける `procurement_available`、条件と台数で申し込む `inv_rental_apply()`（個体の割当はサーバー側）、取り寄せぶんを後から割り当てる `inv_rental_allocate()`。取り込み済み画像の縮小指定（`_ex=`）も元サイズに直します。**冒頭の §32-0 で、このファイルが使う共通関数（`inv_img_hires()` `inv_norm_model()` `inv_norm_url()` ほか）を先に作り直します** — `rakuten-image-sync.sql` は適用後にこのリポジトリ側で追記されており、本番には古い版が当たっているため |
| `2026-09-19-rakuten-orders.sql` | 楽天の受注を在庫につなぐ。`inventory_sale_orders`（注文番号×明細番号×連番で一意）、`inv_sale_orders_apply()`（在庫→販売予約、発送済みなら売却済）、`inv_sale_order_link()`。**あわせて社内用ビュー `inv_channel_stock_feed` を anon から見えないようにします**（Supabaseの既定権限で公開キーから読めていました）。Edge Function `rakuten-order-sync` のデプロイも必要 |

### 使う人と権限

`inventory_members` に登録したアドレスだけが権限を持ちます。**表に無いログインは自動的に「閲覧」**です。

| 権限 | できること |
|---|---|
| 管理者（admin） | すべて。商品登録・廃棄・マスタ編集を含む |
| 一般（member） | QR読取・貸出・返却・移動・入出庫・棚卸（登録と廃棄は不可） |
| 閲覧（viewer） | 参照だけ。操作ボタンはすべて押せない |

社員を足すときは、Supabase の Authentication でアカウントを作り、`inventory_members` に1行入れます。

```sql
insert into inventory_members (email, display_name, role)
values ('yamada@8grp.co.jp', '山田 太郎', 'member');
```

### 値を変える操作は必ず関数を通す

画面から `inventory_items` や `inventory_products` を直接UPDATEしません。
「値を変える」と「履歴を残す」が必ず同じトランザクションになるよう、すべてSupabaseの関数を通します。

| 関数 | 使うところ |
|---|---|
| `inv_item_op()` | 貸出／返却／移動／状態変更／売却／廃棄／棚卸確認 |
| `inv_item_price()` | 仕入価格・手数料・販売予定価格を直す |
| `inv_listing_set()` | 販売サイトごとの出品情報を入れ直す（1台ぶん／型番まとめて） |
| `inv_listings_import()` | 既存在庫CSVの出品状態を移す（**入っている値は上書きしない**） |
| `inv_product_move()` | 入庫／出庫 |
| `inv_product_adjust()` | 棚卸調整（数えた実数に合わせる） |
| `inv_next_id()` | 管理番号の採番 |
| `inv_start_stocktake()` / `inv_close_stocktake()` | 棚卸の開始と終了 |

関数の中で状態も見ます。貸出中でないものは返却できず、在庫より多い出庫は通りません。
採番は `update ... returning` で取るので、同時に登録しても番号がぶつかりません。

> 3セッションから同時に240回採番して、重複も抜けもないことを確認しています。

`inventory_transactions`（履歴）には **UPDATE と DELETE の権限そのものを与えていません**。追記だけです。

### 棚卸

対象の範囲（拠点・部屋・棚）を決めて開始すると、その配下の機器が「未確認」に並びます。
**連続読取**にすると、読み取っても画面が移らず、確認済みの数だけが増えていきます（同じQRの読み直しは1.8秒無視）。
実施中の棚卸は同時に1つだけです。

数量品は数えた実数を入れると、差があっても実数に合わせて「棚卸調整」として履歴に残ります。

### データの持ちかた（3階層）

**型番＝商品／管理番号＝実物1台／状態・症状＝その個体の情報**、という構成です。
型番・商品単位の「商品マスタ」を上に置き、そこに個体と販売情報をぶら下げます。

```
商品マスタ（inventory_products）   型番・商品名・メーカー・スペック・管理方式
  └ 個体在庫（inventory_items）     1台＝1レコード。管理番号・シリアル・保管場所・状態・値段
      └ 出品（inventory_channels）  販売サイトごとの 出品状態・SKU・販売価格・商品URL
```

**出品は実物1台ごとに持ちます。** 売れるのは1台ずつなので、そこに揃えています。
`inventory_channels.item_id` が入っている行が1台ぶんの出品情報です。
`item_id` が空の行は「型番まとめての出品情報」で、1台ぶんの設定が無い個体すべてに当たります。
移行前のデータは型番単位でしか無いので、その受け皿でもあります。

値段は個体（1台）ごとに持ちます。仕入も売却も1台単位で起きるので、そこに揃えています
（→[仕入CSVの取り込みと値段](#仕入csvの取り込みと値段)）。

番号の役割は混ぜません。それぞれ別の項目です。

| | |
|---|---|
| `inventory_products.code` | **商品コード**。DBが採番し、QRのURLに入る |
| `inventory_products.source_code` | 取込元の商品ID（CSVに書いてあった番号）。主キーではない |
| `inventory_items.id` | **管理番号**。実物1台に対応する |
| `inventory_items.source_id` | 仕入先の個品ID |

**CSVの商品IDを主キーにはしません。** CSVの番号は手元のメモでしかなく、DBの主キーと同じとはかぎらないためです
（以前ここを直結していて `inventory_products_pkey` の重複が出ていました）。

**個体管理の現在庫は手入力しません。各個体の状態から数えます。**
手で入れた数と現物がずれるのを防ぐためで、`inventory_stock_view` が計算します。

| 数え方 | 対象 |
|---|---|
| 現在庫 | 在庫・出品中（まだ手元にあり、すぐ出せる） |
| 登録数 | 廃棄・売却済をのぞいた、持っている台数 |

状態は 在庫／出品中／社内使用／貸出中／修理中／故障／紛失／売却済／廃棄／不明。
`kind='quantity'`（数量管理）のマスタだけは `qty` をそのまま在庫数に使います。

### 画面

### データの基準は「自社落札CSV」

```
自社落札CSV（毎週）→ 商品・個体を登録 → QR発行 → 在庫一覧 → 出品サイト登録 → 販売 → 在庫が減る
```

**在庫一覧CSVから商品を作るのではなく、自社落札CSVで仕入れた商品が在庫一覧になっていく**、
という向きです。既存の在庫一覧CSVは初期移行と照合（現在庫・保管場所・販売状況・Notion URL・
過去の備考を補う）に使います。

**既存在庫CSVは仕入の情報を書き換えません。** 管理番号・S/N・仕入価格・原価は自社落札CSVが持ち、
既存在庫CSVの取込では足りない個体を足すだけです。

CSV間の照合は **管理番号・個品ID → S/N → そろえた型番** の順で見ます。
同じ型番でも個体は1台ずつ別に管理します。

| | |
|---|---|
| 商品マスタ | `PROBOOK445G11` |
| 個体 | `0003976995` / `0003977001` / `0003977012` |

### 画面

**在庫一覧** — 上のタブで切り替えます。既定は個体別です。

```
個体別 | 型番別 | 楽天 42 | Amazon 31 | メルカリ 18 | ヤフオク 0 | ヤフーフリマ 0 | 未出品 27
```

販売サイトのタブは、**そのサイトに出品中の個体だけ**を出します。［未出品］はどこにも出していない個体です。
件数はいま掛けている絞り込みのなかで数えるので、タブを切り替えても数は動きません。
タブの状態はURLに残ります（`?view=individual` `?view=model` `?channel=rakuten` `?channel=none`）。
読み込み直しても、リンクを送っても同じタブが開きます。

個体詳細（`/zaiko/items/:管理番号`）では、右側に**商品写真とQRコード**を縦に並べます。
写真は個体ごとに持たず、`product_code` から商品マスターの画像を見ます
（同じ商品の個体が10台あっても参照する写真は1枚）。画面を開くときに楽天APIは呼びません。
在庫管理の画面なので、8RENT用の画像より一般の商品画像を優先します：
`image_url` → `images[0]` → `rental_image_url` → `rental_images[0]` → 「画像準備中」。
楽天に掲載しているのに写真が無いときは、管理者に「楽天画像を同期」への導線だけ出します。

*個体別*（実物1台＝1行）— チェックボックス・管理番号・型番・メーカー・仕入日・原価・販売予定価格・
**出品先**・保管場所・状態・**8RENT** の11列。左端のチェックで選ぶと、画面下にまとめて操作するバーが出ます
（→「在庫一覧からまとめて操作する」）。8RENT列は、その1台をレンタルに回しているか（`レンタル対象`／`対象外`）です。
**商品名は出しません。** 詰め込まず、S/N・CPU・RAM・ストレージ・状態や症状・仕入情報・
サイトごとの出品情報・QR・操作履歴は、行をクリックした先の個体詳細で見ます。
**数量管理の品目は個体を持たないので、1品目1行で数だけ出します。個体管理の行と混ざっても
取り違えないよう、管理番号の欄は「―（数量管理）」、状態の欄は「在庫 42」のように数まで出し、
行の地の色も変えます。**

```
00039769953  PROBOOK445G11  ＨＰ  2026/09/15  ¥52,600  ¥69,800  [楽][Am]  柏 / 倉庫  在庫
―（数量管理）  CBL-LAN6-1M    サンワ  ―         ¥480      ―        —        本社 / 倉庫  在庫 42
```

**出品先はサイト名を長く出さず、小さなバッジだけ**を並べます。出しているサイトだけが付きます
（出品停止・売り切れ・販売済み・保留は付きません）。
**販売サイトのタブで絞っているときも、ほかのサイトに出していればそれも全部出します。**
楽天タブの中でも `[楽][Am]` と出る、ということです。

*型番別*（型番でまとめる）— **型番・管理番号**・メーカー・カテゴリ・現在庫・登録数・**出品先**・保管場所・
在庫状態・最終更新・在庫を動かす、の11列。まとめて直す・まとめて消すはこちらで使います。
出品先は、ぶら下がる個体のどれか1台でも出していればそのサイトが付きます。

先頭は**型番**です。型番が商品の基準なので、商品名は列として持ちません
（型番と違うときだけ小さく添えます。`16-AG0005AU` のように同じなら二重に出しません）。
管理番号は先頭2件と残りの件数を出します。個体が1台も無い商品は**「個体なし」**と赤く出るので、
取込が途中で止まった商品にすぐ気づけます。

検索は型番・商品名のほか**管理番号やシリアル番号でも引けます**。
絞り込みはカテゴリ／メーカー／保管場所／状態。
**販売サイトでの絞り込みは上のタブでやるので、「出品状態」のプルダウンは置いていません。**

右上は **［CSVダウンロード］［商品取込］［CSV取込履歴］** の3つだけです。
使う人から見れば「商品・在庫を足す」は1つの操作なので、入口も1つにまとめています
（→[商品取込](#商品取込)）。

**在庫を動かす** — 型番別の一覧の右端と、商品詳細の基本情報から動かせます。

| | |
|---|---|
| 数量管理 | ［入庫］［出庫］で増減、［数を直す］で数えた実数に置き換え |
| 個体管理 | ［売れた］で台数を入れると、**管理番号の若いものから売却済にして在庫を引きます**。［数を直す］で実数を直接入れられます |

**現在庫は各個体の状態から自動で数えますが、実数を直接入れることもできます。**
個体管理は数そのものを持たないので、入れた数に**個体をそろえます**。

| | |
|---|---|
| 減らす | 在庫・出品中のものから、選んだ状態（既定は「不明」。紛失／社内使用／廃棄も選べる）にする |
| 増やす | 管理番号を採番して足す（管理者のみ） |

**どの管理番号がどうなるかは、確定前にすべて出します。** 数だけ静かに変わる、という形にはしていません。
±ボタンでの増減もできます。変更は1台ずつ履歴に残ります。

売却は1台ずつ `inv_item_op` を通すので、販売価格も履歴も個体ごとに残ります。
どれを売ったか選びたいときは、商品詳細の個体一覧から1台ずつ操作します。

**商品詳細** — 4タブ。「一覧はシンプル、詳細に入るとすべて分かる」形にしています。

| タブ | 中身 |
|---|---|
| 基本情報 | 型番・メーカー・スペック・備考・旧データ備考。数量管理はここで入出庫 |
| 個体一覧 | 1台ずつQR付きで並ぶ。「操作」から貸出・返却・移動・修理・売却・廃棄 |
| 販売情報 | サイトごとの出品中の台数と、型番まとめての設定。下に1台ずつの出品先 |
| 履歴 | その商品と、ぶら下がる全個体の履歴 |

**個体詳細の「出品先」** — 1台ぶんの出品をここで持ちます。

| | |
|---|---|
| 販売サイト | 楽天／Amazon／メルカリ／ヤフオク／ヤフーフリマ／その他／Notion |
| 出品状態 | 出品中／出品停止／売り切れ／販売済み／保留（空にすると**未出品**＝行ごと消えます） |
| 持てるもの | SKU・商品管理番号／販売価格／商品URL／メモ |

1台ぶんの設定が無いサイトは、**型番まとめての設定**がそのまま当たり、行に「型番まとめての設定」と添えます。
出品状態が変わったときだけ履歴に残します（SKUの打ち直しで履歴が埋まらないように）。

### 商品取込

**［既存在庫CSV取込］［自社落札CSV取込］［商品登録］の3つを、［商品取込］1つにまとめています。**
使う人から見れば、どれも「商品・在庫を追加する」操作だからです。

**開くモーダルは1つで、中のタブで切り替えます。画面遷移はしません。**

| タブ | 中身 |
|---|---|
| CSVから取り込む | ドラッグ＆ドロップかファイル選択。**列の名前を見て自動で見分けます** |
| 1件だけ登録 | CSVに載らないものをその場で手入力。商品登録画面と同じ項目・同じ関数を使います |

「1件だけ登録」タブは個体管理／数量管理を切り替えられ、発行予定の管理番号もその場で見えます。
［登録してQR発行］を押すと、**モーダルだけ閉じて一覧にすぐ反映されます**（画面は移りません）。

**「どちらのCSVですか？」とは聞きません。**

| 見分けかた | |
|---|---|
| 自社落札CSV | `開催日`・`出品番号`・`個品ID`・`落札価格` |
| 既存在庫CSV | `商品ID`・`型番`・`管理番号一覧`・`現在庫` |

新規の仕入れは毎週、**自社落札CSV**を取り込む運用が基本です
（→[仕入CSVの取り込みと値段](#仕入csvの取り込みと値段)）。
既存在庫CSVは過去データの初期移行・補完用で、ふだんは使いません。

**商品登録** — 2つの入れかたを、使う頻度の順に置いています。

| | |
|---|---|
| 1. 仕入CSVでまとめて登録 | **毎週使うメインの導線。** 画面の主役として上に置き、ここだけライムのボタンにしています |
| 2. 1件ずつ商品登録 | CSVに載らないものを手で足すときの**例外**。下に従として置きます |

直近の取込は「最終取込 2026/09/15 17:30」のように小さく出します。取り込んだ直後は
**「今回登録した商品 ○件」**をこの画面にも在庫一覧にも出して、結果がすぐ分かるようにしています。

1件ずつのフォームは上部の「個体管理／数量管理」で内容が変わります。
同じ型番がすでにあれば**マスタは増やさず、その商品の個体として足します**。

### 在庫と販売サイトの関係

**自社在庫DBが正です。** 楽天・Amazonなどは販売チャネルでしかありません。
**販売サイト側の在庫数を、そのまま自社在庫へ上書きすることはしません。**

合わないときは「**在庫差異**」として出します。

```
⚠ 在庫差異 3台 — 手元に無いのに、販売サイトでは出品中のままです。   [ 確認する ]
```

売却済・廃棄にしたのに、その1台がまだ出品中のまま残っている、という形です。
一覧の上に出て、［確認する］でその個体だけに絞れます。行の左端にも印が付きます。

売却・廃棄を記録した直後にも同じことを知らせます。

> 1台が**売却済**ですが、販売サイトではまだ**出品中**のままです。
> 在庫の数は自社のデータが正です。販売サイト側の出品停止を確認してください。
> 　　　　　　　　　　　［あとで］［出品を止めたことにする］

［出品を止めたことにする］で、その個体の出品中のサイトをまとめて出品停止にします。

### 入庫・出庫

**入庫＝モノが増える・戻ってくる、出庫＝モノが減る・手元から出る**、という考え方でそろえています。

| | 入庫 | 出庫 |
|---|---|---|
| 数量管理 | `qty` を足す | `qty` を引く |
| 個体管理 | 在庫に戻す（貸出中なら返却として記録） | 社内使用／貸出／売却のどれかにする |

**数量管理の入庫と出庫は同じ数字を動かします。** どちらも `inv_product_move()` を通り、
在庫が10のときに入庫5で15、出庫3で12、というように連動します。履歴には前後の値が残ります。

個体管理は台数を足し引きしません。**現在庫は各個体の状態から数える**ので、
状態が変われば現在庫は自動で変わります。

### QRを読んで入庫・出庫

入庫・出庫の画面いちばん上の「QRを読んで入庫／出庫」から、**続けて処理できます**。

1. QRを読む
2. 確認のシートが出る（数量品は数、個体は出し先）
3. 確定すると**スキャナに戻る**ので、そのまま次のQRを読める

読み取りのあいだはカメラを止めるので、同じものを二重に記録しません。
上部に「出庫 3件」のように、その回で処理した数が出ます。
すでに在庫のものを入庫しようとしたり、売却済のものを出庫しようとすると、その場で知らせます。

### 在庫一覧からまとめて操作する（個体別）

個体別の一覧では、左端のチェックで**実物1台ずつ**選びます。
ヘッダーのチェックは「いま絞り込みで表示している個体」だけを全選択します
（状態・保管場所・カテゴリ・8RENTの絞り込みと組み合わせて使えます）。

1件以上選ぶと、画面下に固定のバーが出ます（スクロールしても操作できます）。

```
☑ 3件選択中 ｜ 8RENTに出す ｜ 貸出 ｜ 売却 ｜ 修理 ｜ 棚卸 ｜ 廃棄 ｜ 選択解除
```

PCは1段、スマホ（375〜390px）は「件数＋選択解除」と操作ボタン2段に折り返します。

| 操作 | すること | 受け付けない個体 |
|---|---|---|
| 8RENTに出す | 個体を `rental_eligible = true`（レンタル対象）にする。商品がまだ8RENT非掲載なら**あわせて掲載ONにする**（最初の1台で自動） | 売却済・廃棄 |
| 8RENTから外す | 個体を `rental_eligible = false` に戻す（販売用として在庫に残る）。**商品の掲載設定には触らない** | 売却済・廃棄・**予約中**（先に申込をキャンセル）・**貸出中**（先に返却） |
| 貸出 | `在庫 → 貸出中`。貸出先（必須）・返却予定日・メモを入れる | 「在庫」以外 |
| 売却 | `→ 売却済`（販売済み）。確認モーダルは必須。販売価格を入れると1台ずつ記録される | 予約中・貸出中（先に返却／キャンセル）・売却済・廃棄 |
| 修理 | `→ 修理中`。理由・メモを入れられる | 売却済・廃棄・予約中・販売予約・修理中 |
| 棚卸 | **状態は変えません。**「現物確認済み」として記録（実施日時・実施者・対象個体・結果が履歴に残り、`last_checked_at` と棚卸セッションにも入る） | 売却済・廃棄 |
| 廃棄 | `→ 廃棄`。確認チェックが必須で、理由も残せる。管理者のみ | 廃棄済み |

実行はサーバー側の `inv_items_bulk_op()` が1台ずつ行います。**1台が失敗しても他は進みます。**
1台ごとの検証と履歴はこれまでどおり `inv_item_op()` に任せているので、
1台ずつ操作したときと同じ規則・同じ履歴になります。

終わると結果が出ます。

```
8RENT対象に5台追加しました
3台中2台成功・1台は貸出中 のため8RENTから外せません（先に返却してください）   ← 失敗は理由つきの一覧も出る
```

できなかった個体は選んだままにするので、状態を直してそのまま再実行できます。

外した結果その商品のレンタル対象が0台になったときは、**掲載は落とさずに知らせます**
（「◯◯はレンタル対象が0台になりました。掲載はそのままです」）。8ECでは「在庫切れ」になり
申込はできません。掲載自体を止めるかどうかは、商品詳細の「8RENT設定を変える」で人が決めます。

#### 1台ずつ切り替える（個体詳細）

`/zaiko/items/:item_id` の操作にも **「8RENTに出す」「8RENTから外す」** があります。
使っているのは在庫一覧のまとめて操作と**同じRPC・同じ検証ルール**（`inv_items_bulk_op`）で、
詳細画面のための別ロジックは持ちません。予約中・貸出中は「外す」を押せず、
理由がボタンに出ます。押したあとは画面を読み込み直さずに、バッジとボタンだけが切り替わります。

### 一覧から一括で直す・消す

在庫一覧の各行にチェックボックスがあります。選ぶと下にバーが出て、まとめて操作できます。
見出しのチェックで**いま絞り込んで表示している分**を全部選べます。

**まとめて直す**（一般メンバー以上）

チェックを入れた項目だけを変えます。入れていない項目はそのままです。

| 項目 | 補足 |
|---|---|
| カテゴリ | ぶら下がる個体のカテゴリもそろえます |
| メーカー | 同上 |
| 保管場所 | **個体も一緒に動かすか**を選べます。動かす場合は1台ずつ履歴に残します |

取り込んだ直後はカテゴリも保管場所も全件が同じになるので、ここで分けていくのが実際の使いかたです。
売却済・廃棄の個体は、もう手元に無いので動かしません。

**まとめて削除**（管理者のみ）

選んだ商品を、ぶら下がる個体と販売情報ごと消します。
消す前に内訳を出し、**「削除します」と入力するまでボタンが押せません**。
何を消したかは商品ごとに履歴へ残ります。

### 在庫データの削除

取り込みをやり直したいときのために、在庫一覧のいちばん下に置いています。**管理者だけ**です。

- 「すべて消す（商品マスタ・個体・販売情報）」と「個体だけ消す」を選べます
- 確認のため **「削除します」と入力するまでボタンが押せません**
- **履歴は消えません。** 追記のみの記録なので、いつ誰が何を消したかもここに残ります
- 実施中の棚卸があるときは断ります（中途半端になるため）

> **SQLを書き足すときの注意：** Supabase には「WHEREのないDELETE/UPDATE」を禁止する保護
> （safeupdate）があり、入っていると**関数の中でも**弾かれます
> （`DELETE requires a WHERE clause`）。全行が対象のときも WHERE を書いてください。
> ただし `where true` や `where 1=1` はプランナに畳み込まれて消えるため保護をすり抜けられません。
> 主キーへの `is not null` のように、プランに Filter として残る条件を使います。
>
> ```bash
> python3 tools/check-sql.py     # WHEREのないDELETE/UPDATEが無いか点検する
> ```

### 在庫一覧のCSV

在庫一覧から、いま絞り込んでいる分をCSVに書き出せます。Excelでそのまま開けるBOM付きUTF-8です。

**取り込みは「足すだけ」です。すでにある在庫は書き換えません。**
在庫の数や状態は入庫・出庫・貸出といった操作で動かすものなので、
表計算の上書きで静かに変わると履歴と現物が合わなくなります。
そのため、CSVにあって在庫に無いものだけを新規登録します。

- 既にある行（同じ管理番号／商品コード、または同じシリアル番号・品名）は**そのまま**
- 管理番号が空の行は**採番して**追加します（Excelで一覧を作ってまとめて登録できます）
- カテゴリと保管場所は**名前**で書きます。保管場所は `本社 / 倉庫 / 棚A-01` でも `棚A-01` でも可
- 同じ名前の場所が複数あるときは取り違えないよう取り込まず、候補を出します
- Shift_JIS のCSV（Excelから出したもの）も自動で判別して読みます

取り込む前に「追加する／すでにある／取り込めない」の件数と中身を出すので、
何が起きるかを見てから確定できます。取り込めない行は理由つきで一覧されます。

書き出した列はそのまま読み戻せるので、**ダウンロード → Excelで追記 → 取込**の往復ができます。
同じCSVを2回入れても増えません。

### 重複スキップは黙って消さない

すでにある管理番号（CSVの中で重なっているものも、DBにすでにあるものも）は登録しません。
**ただし黙って件数だけ減らすことはせず、必ず結果に出します。**

一覧に戻ると出る「今回登録した商品 ○件」の帯に、重複スキップの件数と**詳細を見る**が並びます。

```
今回登録した商品 373件
個体 373台　2026/09/16 22:21　仕入0916.csv
重複スキップ 2件  詳細を見る
```

詳細では、飛ばした**管理番号・スキップ理由・CSVの行**を1件ずつ確認できます。

| スキップ理由 | 意味 |
|---|---|
| すでに在庫にあります | その管理番号はDBにもう登録済み |
| ○行目にすでにあります | 同じ管理番号がCSVの中で2回以上出てきた |
| S/N ○○ が○○と同じです | 個品IDは違うが、S/Nが一致＝同じ実物 |

同じ内容は**CSV取込履歴**にも残ります。履歴の一覧に「重複スキップ」列があり、
件数のボタンから同じ詳細を開けます。

**S/Nでの一致判定は、明らかに未記入の代わりに入っている値では行いません。**
`不明` `フメイ` `-` `N/A` `NONE` のような値や、`0000000000` のように同じ文字の
繰り返しだけの値は、同じ実物を指す証拠にならないためです。これらのS/Nを持つ個体は
何台あっても互いに重複扱いにせず、そのまま登録します（保存する値そのものは変えません。
一致判定にだけ使いません）。

### 取り込めないときの直しかた

取り込めない行は、**理由ごとにまとめて件数を出します**。

```
取り込めない 187件
  178  保管場所が未登録      「柏倉庫」175件 → [ 柏 / 倉庫 ▾ ]
                              「市川」3件     → [ 選んでください ▾ ]
    9  カテゴリの管理方式が違う 「入力機器」5件 → [ その他IT機器 ▾ ]
```

右の欄で**登録済みのものに読み替える**と、その場で取り込めるようになります。
件数はすぐ更新されるので、何件通るようになったかを見ながら決められます。
読み替えはこの取り込みのあいだだけ有効で、CSVそのものは書き換えません。
設定したものは一覧に出て、取り消せます。

理由は次のように分けています。「カテゴリが無い」のと
「カテゴリはあるが管理方式が違う」のは直しかたが別なので、区別します。

| 理由 | 意味 |
|---|---|
| 保管場所が未登録 | その名前の場所が無い |
| 保管場所の名前が複数ある | 末尾の名前だけでは決められない（`本社 / 倉庫` のように書くか読み替える） |
| カテゴリが未登録 | その名前のカテゴリが無い |
| カテゴリの管理方式が違う | カテゴリはあるが、個体管理／数量管理が食い違っている |
| CSVの中で重複 | 同じ商品IDや型番が2行ある |
| 商品名も型番も空 | 商品を特定できない |

### これまでの「統合在庫一覧（型番別）」の取り込み

いま使っている型番別のCSVも、そのまま読み込めます。列を見て自動で見分け、次のように組み替えます。

| 元のCSV | 取り込み先 |
|---|---|
| 型番の行 | 商品マスタ1件（商品名が空なら型番で代用） |
| 管理番号一覧 | 「 / 」で割って**個体1台ずつ**のレコード |
| 出品状況（`Amazon:出品停止/出品中 ｜ 楽天:…`） | 型番まとめての出品情報にサイトごとの行 |
| `Amazon出品状態`・`楽天出品状態`…（サイト別の列） | 同上。`AmazonSKU`・`Amazon価格`・`楽天 URL` も読みます |
| 在庫数・登録台数・在庫状況・備考・元データ在庫内訳 | **旧データ備考**（消さずに残す） |

**出品状態は「出品中」のときだけ一覧のバッジが付きます。** それ以外（出品停止・売り切れ・保留…）は
値としては持ちますが、出品中の印は付けません。「未出品」としか書かれていない列は行を作りません。

**備考に紛れている販売用コードは、できる範囲で出品情報へ分けます。**
`楽天コード: RK-9001` `AmazonSKU B0XXXXXX` のような書き方を拾って、そのサイトのSKUにします。
元の文は消さず、備考にはそのまま残します。

**すでに入っている出品情報は上書きしません。** 空いている欄だけを埋めます
（`inv_listings_import`）。自社落札CSVで作った仕入の情報を、あとから来た表計算で消さないためです。
**商品がすでにあって管理番号が空の行でも、出品状態だけは足します。** 既存在庫CSVを「補完に使う」のは
まさにこの形だからです。

取り込みの際の判断は次のとおりです。

- **在庫数は取り込みません。** 各個体の状態から数えます。手入力の数と現物のずれを持ち込まないためです
  （実データでは207行のうち8行がずれていました）。
- **状態は「元データ在庫内訳」の件数どおりに割り当てます。** ただし
  *どの管理番号がどの状態かは元データに書かれていません*。件数の順で当てているだけなので、
  分からないもの（未設定・不明・なし）は**「不明」**にしています。棚卸で現物を確認して確定してください。
- 同じ管理番号が複数の型番に出てくる場合、**1台だけ**取り込み、残りは旧データ備考に書きます。
- URL列は自由記述が混ざっているので、`http` で始まるものだけURLに、それ以外はメモに回します。
- カテゴリと保管場所は元データに無いので、取り込み画面で選んだものを全件に当てます。

> 実データ（207型番）で確認しています。商品マスタ207件・個体398台・販売情報950件になり、
> 重複していた管理番号2件は1台ずつに寄せられます。

> CSVの読み書きそのものは `assets/csv.js`（管理画面で共通）。`/admin/ec/` のモール連携も同じものを使っています。

### 仕入CSVの取り込みと値段

オークションの仕入のたびに出るCSV（`開催日 / 出品番号 / 構成 / 総数 / 型番 / 落札価格 / 落札料 / 個品ID …`）を
そのまま読み込めます。列を見て自動で見分けます。

毎週の作業なので、**在庫一覧 → 仕入CSV取込 → 内容確認 → 一括登録** の4手で終わるようにしています。

```
商品登録［仕入CSVを取り込む］  ← 在庫一覧の［仕入CSV取込］からでも同じ
   → CSVを落とす／選ぶ         ← ドラッグ＆ドロップでもファイル選択でも
   → 内容確認                  ← 新規/既存/登録済み・商品数・個体数・原価・販売予定・想定利益
   → ［一括登録］
   → 在庫一覧（今回登録した商品 ○件 だけ表示）
```

確認画面に出す件数は次のとおりです。**同じCSVを誤ってもう一度上げても二重登録になりません**
（管理番号＝個品IDがすでに在庫にあるものは「登録済み」に入り、登録の対象から外れます）。

| | |
|---|---|
| 新規商品 | このCSVで新しく作る商品 |
| 既存商品への追加 | すでにある商品（または同じCSV内で作った商品）に個体だけ足す仕入 |
| 個体 | 登録する台数 |
| 登録済み | 管理番号がすでに在庫にある仕入。何もしません |
| 重複・取り込めない | 型番が無い、CSVの中で重なっているなど |

保管場所は仕入CSVに入っていないので、確認画面で選んだものを全件に当てます。
初期値は **柏倉庫**（`柏 / 倉庫`）で、取り込む前に変えられます。

取り込んだあとは在庫一覧に戻り、**「今回登録した商品 ○件」**を出してその商品だけを表示します。
「すべて表示」で解除できます。商品登録の画面に戻っても同じ件数が出るので、結果を見失いません。
「今回」と言うのは取り込んだ直後だけで、あとから取込履歴で同じ回を開いたときは「この取込で登録した商品 ○件」になります。

**CSV取込履歴** — 在庫一覧に小さく置いています。取込日・ファイル名・登録商品数・登録個体数・登録者が並び、
「この分だけ見る」でその回の商品だけを一覧に出せます。`inventory_imports` に残していて、
履歴なので **UPDATE と DELETE の権限は誰にも渡していません**（追記だけ）。

追いかけるのは **仕入れ → 原価が分かる → 売値を決める → 利益が分かる** の1本道だけで、
持つ値段は次の5つに絞っています。

| | |
|---|---|
| 仕入価格 | 落札価格 |
| 手数料 | 落札料 |
| **原価** | 仕入価格 ＋ 手数料（`cost`。**生成列**なので手では入れられない） |
| 販売予定価格 | 取り込み時は原価×1.3を目安に入れる。**その場で必ず直せる** |
| 実際の販売価格 | 売却したときに入る |

想定利益（販売予定価格 − 原価）と利益（実際の販売価格 − 原価）は引き算なので、列は持たずその都度出します。

CSVの組み替えかた：

| 元のCSV | 取り込み先 |
|---|---|
| 出品番号 | 仕入1件（親行に落札価格、子行に個品が並ぶ形）。**同じ型番なら商品は分けず、個体だけ足します** |
| **総数** | **在庫の台数**。この数だけ個体をつくり、QRを発行します |
| 個品ID(バーコード) | 数が総数と合っていれば**管理番号**に使う（現物のバーコードと一致）。合っていなければ**仕入元ID**として残す |
| 落札価格・落札料 | 仕入全体の金額として持ち、登録数量で割って1台ずつに持たせる。端数は先頭の1台に寄せて合計を合わせる |
| 型番 | 商品名と型番（CSVの「商品名」列は出品カテゴリ（`NTPC`/`ｻﾌﾟﾗｲ`）なので使いません） |
| Ｓ／Ｎ | シリアル番号 |
| CPU・RAM・ＨＤ容量・液晶・仕様 | スペック（`ﾅｼ` や `-` は落とす） |
| 状態・症状・詳細・備考・補足 | 個体の備考 |
| 開催日 | 仕入日 |

取り込み確認画面に出すのは **商品名・型番・数量・1台あたり原価・販売予定価格・想定利益** の6列だけです。
**数量と販売予定価格はその場で直せます。** 数量を直すと、登録する個体数・QRの発行枚数・
1台あたり原価・想定利益・合計がすべて付いてきます（CSVの総数から変えたことも欄の下に出ます）。
最終的に確定した数量と、つくられる**個体の数・QRの数は必ず一致します**。
カテゴリと保管場所は仕入CSVに無いので、画面で選んだものを全件に当てます。

商品詳細（個体）に出す値段も **原価・販売予定価格・実際の販売価格・利益** の4つだけです。
「値段を直す」から仕入価格・手数料・販売予定価格を直せます（`inv_item_price`）。
売却するときは実際の販売価格を入れます。原価との差が利益として履歴に残ります。

### 型番に状態や補足が混ざっているとき

元データでは、型番の欄に不具合や持ち主まで書かれていることがあります。
そのままだと**同じ機種が別商品に分かれてしまう**ので、取込時に分けます。

| CSVの型番 | 型番 | 個体の備考へ |
|---|---|---|
| `CF-QV9TFLVS ちゃんと閉められない` | `CF-QV9TFLVS` | ちゃんと閉められない |
| `PROBOOK450G9 (画面割れ）` | `PROBOOK450G9` | 画面割れ |
| `20H7-S0SU00（長筆さんの）` | `20H7-S0SU00` | 長筆さんの |
| `16-AG0005AU` | `16-AG0005AU` | （そのまま） |
| `HDDｾｯﾄ Western Digital` | `HDDｾｯﾄ Western Digital` | （英数字の続きは型番の一部） |

日本語が始まるところ、または日本語の入った括弧で切ります。
英数字だけの続き（`(IdeaPad 520)` `Western Digital` など）は型番の一部として残します。
切ったときは**元の型番表記も個体の備考に残す**ので、元データは失われません。

実データ（207行）では17行が該当し、**207型番 → 187商品**にまとまりました。
`PROBOOK450G9` は5行が1商品になり、起動できない／キーボード外れ／画面割れは
それぞれの管理番号の備考に入ります。

### 商品はあるのに個体が無いとき（個体補完）

取込が途中で止まると、商品マスタだけができて個体が入らず、**現在庫0・登録数0**になります。
一覧では **「個体なし」** と赤く出ます。

直しかたは**同じCSVをもう一度取り込むだけ**です。商品は型番で見つけて作り直さず、
**まだ入っていない管理番号だけ**を足します。確認画面に「足りない個体を補います」と件数が出ます。
何度取り込んでも、すでにある管理番号は増えません。

### 落札価格や個品IDが入っていないCSV

在庫側から出した、列だけ落札CSVと同じ形のCSVがあります。
落札価格が1行も無かったり、個品IDが半分しか無かったりします。
**型番と総数さえあれば取り込めます。**

| 足りないもの | どうするか |
|---|---|
| 落札価格・落札料 | 原価は空のまま登録。あとから個体詳細の「値段を直す」で入れる |
| 個品ID | 総数ぶんの管理番号を発行する（仕入元IDは残すものが無いので空） |
| 総数が 0 | **商品だけ作り、個体は作らない。** 在庫なしとして正しい形。次に仕入れたぶんがこの商品にぶら下がる |

何が分かって何が分からないかは、取り込む前に確認画面に出します。

> 実データ（380行・207出品番号）で確認しています。落札価格は0行、個品IDは154行だけ、
> 総数0が78件、という状態で **204商品・235台**（総数の合計どおり）が入ります。
> 207出品番号のうち3件は他と同じ型番なので、商品は204件にまとまります。

### セット出品（個品ID 1つ・総数 9）

`WKBｾｯﾄ` のように、個品IDは1つでも現物は9個ある、という仕入があります。
**在庫数の基準は個品IDの数ではなく「総数」**です。QRで1台ずつ棚卸するので、個体も9件つくります。

```
WKBｾｯﾄ　総数 9　個品ID 00039586573　落札 36,000＋3,600
  ↓
個体 9件      WKB-00001 … WKB-00009     ← 管理番号を1台ずつ発行。QRも9個で全部ちがう
仕入元ID      00039586573（9台とも）     ← 元の個品IDは残して仕入をたどれるようにする
1台あたり原価 ¥4,400（39,600 ÷ 9）
商品詳細      在庫 9台
```

**同じ管理番号・同じQRを9個つくることはしません。** 棚卸で1台ずつ確認できなくなるためです。
数が合わないときはシリアル番号を付けません（1台を指す番号が9台に並ぶと嘘になるため）。

取り込んだあと、在庫一覧や商品登録の画面から **「今回登録したQRを印刷」** で、
その回に発行したぶんだけをまとめて印刷できます（上の例なら9枚）。

> 原価が入っていない個体では、売値をそのまま利益と書くと嘘になるので、利益は出しません。

同じ型番を別の出品番号で（別の値段で）買うことがあります。**商品は1つにまとめ、個体だけ足します**。
値段は個体ごとに持つので、仕入額が違っても同じ商品にぶら下げられます。
同じ仕入CSVをもう一度入れても**「すでにある」**になり、何も増えません。
管理番号だけでなく**仕入元IDでも照合する**ので、採番して入れたセット出品も二重登録になりません。

### QRラベル

実寸 **40×30mm**。A4に並べて印刷しても、ラベルプリンタでも同じ版を使います。
選択UIは `data-noprint` を付けてあるので、そのまま印刷・PDF出力できます。

### カメラが使えないとき

権限が下りない、HTTPSでない、対応していない――いずれの場合も、
スキャナの下にある**管理番号の手入力**からその機器を開けます。読み取りに失敗してもスキャナは閉じません。

### 元になった設計

`design_handoff_qr_inventory`（QRコード在庫管理システム MVP のデザインハンドオフ）に沿って実装しています。
プロトタイプは localStorage 前提でしたが、ここでは Supabase に置き換え、
権限はクライアント側のトグルではなく `inventory_members` と RLS に接続しています。
色・字送り・余白・タップ領域はハンドオフの指定どおりです。

## チャネルの役割 — 楽天は販売、8ECはレンタル

**楽天＝販売サイト、8EC（トップ・8RENT）＝レンタルサイト**です。
同じ商品・同じ実在庫を両方のチャネルに出しますが、**販売とレンタルは別の公開判定**にします。

- 楽天に出品している商品を、8ECでレンタル対象にできる
- 8ECでレンタル対象にしても**楽天の商品掲載（listing）は解除しない**
- 8ECに載せる条件は `rental_enabled = true` だけ（楽天に出品中かは条件にしない）
- 楽天で受注が入った個体はすぐ `販売予約` にして、8ECの利用可能在庫から外す
- 発送したら `売却済`（＝販売済み）
- 最後のレンタル可能在庫が売れたら、8EC側は自動的に「在庫切れ」になる

大事なのは、**「楽天に掲載しているか」と「楽天でいま買える数量」を分けて持つ**ことです。
レンタル中の商品でも楽天の商品ページは維持しますが、物理的に発送できない個体
（予約中・貸出中・販売予約・修理中）は**楽天へ送る販売可能数量に含めません**。
1台しかない商品が貸出中なら「掲載は残す・購入できる数量は0」が正解です。

| 実在庫の状態 | 8EC（レンタル） | 楽天（販売） |
|---|---|---|
| 在庫 | レンタル可 | 掲載中・購入可（数量に数える） |
| 予約中（レンタル申込・発送待ち） | レンタル不可 | 掲載は維持・数量から外す |
| 貸出中 | レンタル不可 | 掲載は維持・数量から外す |
| 販売予約（楽天で受注・発送待ち） | レンタル不可 | 掲載は維持・数量から外す |
| 売却済（販売済み） | 非表示（台数から消える） | 在庫減少 |
| 修理中・故障・紛失 | レンタル不可 | 数量から外す |
| 廃棄 | 非表示 | 非表示 |

同じ実在庫を二重に確保しないことを最優先にしているので、レンタル予約も販売予約も
サーバー側の `inv_reserve_available_item()`（行ロック＋`for update skip locked`）を
必ず通ります。最後の1台にレンタル申込と楽天受注がほぼ同時に来ても、成功するのは一方だけです。

```
              /zaiko（共通の商品・物理在庫）
                        │
        ┌───────────────┴───────────────┐
      楽天＝販売                       8EC＝レンタル
  掲載は維持・数量だけ増減        rental_enabled で公開・在庫があれば申込可
```

### 8RENTの借りかた — 個体ではなく「条件で選ぶ」

お客様は管理番号も商品コードも選びません。**条件に合う機種**と**台数**を選ぶだけで、
どの1台を貸すかは `inv_rental_apply()` が在庫から決めます。

- **同じメーカー＋型番は1機種**。メモリ違い・Office有無で商品コードが分かれていても、
  カードは1枚です（`inv_model_key()` ＝ `inv_norm_model(maker)/inv_norm_model(model)`）。
  仕様の違いは商品詳細の中で選びます。同じ型番のカードが2枚並ぶことはありません。
- **条件で絞る**：CPU・メモリ・ストレージ・画面サイズ・Office・カメラ・テンキー・台数・利用期間。
  スペックが書いていない項目は「合わない」ではなく「分からない」なので、
  その条件を指定されたときだけ落とします。
- **Officeは商品ではなくオプション**。申込時に「Officeを付ける」を選ぶと、
  Office対応の枝番からだけ割り当てます。
- **在庫0でも申し込める**（商品の `procurement_available` が true のとき）。
  8RENTには「取り寄せ可能」と出て、申込は `調達確認` から始まります。
  **在庫が無いのに仮の個体を作って予約することはしません。**

```
在庫がある      申込（個体を確保・予約中）  →  発送＝貸出確定  →  返却済み
取り寄せ        申込  →  調達確認  →（現物を /zaiko に登録して8RENT対象にする）
                      →「個体を割り当てる」（inv_rental_allocate）→ 申込  →  貸出確定
```

`/zaiko` の「8RENT申込」画面に台数・取り寄せ台数・割り当てた個体が出ます。
`調達確認` のままでは発送できません（先に「個体を割り当てる」を押してください）。
取り寄せの可否は、商品詳細の「8RENT設定を変える」→「取り寄せ可」で切り替えます。

### 楽天で売れたとき（販売予約 → 販売済み）

**画像・商品情報の同期（Rakuten Developers API）では注文は取れません。**
受注は **RMS WEB SERVICE の Order API** という別のAPI・別の資格情報です。
在庫一覧の **「楽天の注文を取り込む」**（Edge Function `rakuten-order-sync`）で取り込みます。

```
楽天で受注  →  /zaiko「楽天の注文を取り込む」（rakuten-order-sync）
             →  RMS searchOrder → getOrder で明細を取る
             →  inv_sale_orders_apply（注文番号×明細番号×連番で冪等）
             →  inv_sale_reserve → 個体が 在庫 → 販売予約
                （8ECのレンタル可能数からも楽天の販売可能数量からも即座に外れる）
             →  発送済みで届いた注文は そのまま 売却済（＝販売済み）
             →  キャンセルで届いた注文は 販売予約 → 在庫 に戻す
```

| 決めごと | 中身 |
|---|---|
| 冪等 | `inventory_sale_orders` に **注文番号 × 明細番号 × 明細内の連番** で一意制約。同じ注文を何度取り込んでも在庫は一度しか減りません。同時に2回届いても、明細ごとに先に鍵をかけてから在庫を取ります |
| 二重確保しない | 確保は8RENTの申込と共通の `inv_reserve_available_item`（`for update skip locked`）。**8RENTで予約中・貸出中の個体は `status='在庫'` ではないので、そもそも楽天の受注では取られません** |
| 商品の特定 | `external_item_code` の一致か、正規化した掲載URLの一致だけ。**URLやSKUから推測しません** |
| 特定できないとき | 在庫を動かさず `未割当` で記録して知らせます（`inv_sale_order_link()` で人が商品を当てられます） |
| 在庫が足りないとき | `在庫なし` で記録して知らせます。**仮の個体は作りません** |

手で記録したいときは、これまでどおり商品詳細の「受注を記録」（`inv_sale_reserve`）も使えます。

**必要な設定**

```bash
supabase functions deploy rakuten-order-sync
# RMSの「Web APIサービス」で発行する資格情報（画像同期のものとは別）
RAKUTEN_RMS_SERVICE_SECRET
RAKUTEN_RMS_LICENSE_KEY
```

`inv_sale_reserve()` は商品の掲載（`inventory_channel_listings`）を変更しません。
**受注が入っても楽天の商品ページは残し、減らすのは数量だけ**という考え方です。

### 楽天へ送る販売可能数量

`inv_channel_stock_feed`（社内用ビュー・`authenticated` のみ）に、チャネルごとの
`sale_qty`（＝掲載中なら `status='在庫'` の個体数、未掲載なら0）と、その内訳
（予約中・貸出中・販売予約・修理中の台数）が出ます。`/zaiko` の商品詳細「販売情報」タブでも、
サイトごとに「販売できる数量」を表示します。楽天の在庫数はこの数量に合わせて更新してください
（掲載は消さない）。

## トップページ（/）＝ 8RENT — 自社在庫のレンタル公開

**ルート `https://www.8ec.jp/` は 8RENT のページです。**
デザインはデザインZIP同梱の 8RENT（`8RENT 法人PCレンタル.html` / `8RENT.dc.html`）を正とし、
ロゴ・見出し・CTA・バッジ・写真・セクションの順序をそのまま再現しています。
購入とレンタルを並列にした「8EC総合トップ」への作り替えは採用しません（2026-09 に差し戻し）。
購入は、比較セクションと商品詳細の**補助導線**としてだけ出します。

以前の `/rental/` は同じ内容なので、`vercel.json` の `redirects` で `/` へ 308 転送します
（`?code=…` もそのまま引き継ぎます。設定が効かない環境向けに `rental/index.html` に控えの転送HTMLを残しています）。

セクションの順序（HTMLもこの順）：
8RENTヘッダー → ヒーロー（法人PCを、まず1台からお試し。）→ 法人向けPC 1カ月お試しレンタル →
届いたらすぐ使える → 借りるだけで会社のITが一歩進む → お試しの流れ → 購入・リース・レンタルの比較 →
通常のIT機器レンタル（カテゴリー・条件検索・おすすめ商品）→ 用途から探す → 法人向けサービス →
企業向けパッケージ → ネットワーク・IT環境 → 8RENTの特徴 → eラーニング・Supported Plan →
導入事例 → FAQ → 申込・相談（`#contact`）→ 最終CTA → 8RENTフッター

商品・写真・在庫・月額は `/zaiko` が管理するデータを、**公開ビュー `inv_public_catalog`** から読みます。
トップ専用の商品マスターや、販売用・レンタル用の別在庫は持ちません。取得・写真の選び方・在庫の判定・
ボタンの出し分けは `assets/catalog.js`（`window.EightCatalog`）に1か所にまとめています。
商品名・写真・価格・在庫数・カテゴリー件数をHTMLに固定しないでください（デザインHTMLの `PRODUCTS` 配列は見本です）。

```
楽天同期（rakuten-product-sync）／ /zaiko での登録・編集・在庫操作
                      ↓
  inventory_products（商品・画像・rental_*）＋ inventory_items（個体）＋ inventory_channel_listings（出品）
                      ↓  inv_public_catalog（公開してよい列だけ・anon が select）
                      ↓  assets/catalog.js（EightCatalog）
             トップ（/）＝ 8RENT
        ── rental_enabled = true の商品だけ ──
```

| 表示項目 | 取得元 |
|---|---|
| 商品名・型番・メーカー・カテゴリ・スペック（CPU/メモリ/ストレージ…） | `inventory_products`（＋`inventory_categories.name`） |
| 代表画像 | `image_url`（人が指定したメイン画像）→ `images[0]`（楽天同期・手入力）→ 無ければ「画像準備中」 |
| 8RENT用の写真 | `rental_image_url` / `rental_images` → 無ければ上の一般画像 |
| いま提供できる台数 `available` | `inventory_items` の `status = '在庫'` の個体数（予約中・販売予約・貸出中・修理中・故障などは含めない） |
| 楽天に掲載しているか・購入先・価格 `sale_listed` | `inventory_channel_listings`（`channel='rakuten'`・`state='出品中'`・登録済み `url` あり）。ボタンは「楽天市場で購入」で、URLは商品コードから推測しない |
| 楽天でいま買える台数 `sale_available` | 掲載中なら `status = '在庫'` の個体数、未掲載なら 0。発送できない個体（予約中・貸出中・販売予約・修理中）は含めないので、最後の1台が貸出中なら**掲載あり・0台**になり、購入ボタンは出しません |
| レンタルできるか・月額・最低期間・Office・お試し | `inventory_products` の `rental_enabled` / `rental_price_month` / `rental_min_months` / `office_supported` / `trial_eligible` |
| カテゴリー件数 | 公開商品から集計（「N 機種」＝商品数、「在庫 N 台」＝提供可能数の合計。実在するカテゴリーだけ） |
| 購入／レンタルのボタン | レンタルが主（カードは「申し込む」＝商品詳細のレンタル申込）。購入は商品詳細の下に「楽天市場で購入」を1行だけ出す補助導線で、買える台数が0なら「購入について相談する」に切り替える。レンタルできる台数が0なら申込フォームは出さない |

### 「一覧に載せる条件」と「申し込める条件」は別

| | 見るもの | 意味 |
|---|---|---|
| 一覧に載せる | 商品 `rental_enabled = true` | レンタル商品として公開する（楽天に出品中かは条件にしない） |
| レンタルを申し込める | `rental_available > 0` | 個体 `rental_eligible = true` かつ `status='在庫'` が1台以上ある |

レンタルは**商品と個体の2段階**で決まります（→「8RENTに出す個体を選ぶ」）。
`rental_enabled` がオンでも `rental_available = 0` なら、カードは「在庫切れ」で申込ボタンを出さず、
商品詳細も申込フォームではなく「入荷のご相談をする」に切り替わります。条件検索・おすすめ商品も
`rental_available` で判定します（`available` ではなく必ずこの列を見る）。

**楽天で最後の1台が売れたとき**は、`inv_sale_reserve()` がその個体を `販売予約` にするので
`rental_available` が 0 になり、8ECの申込ボタンは次の読み込みで消えます。
**楽天の掲載（listing）はそのまま**で、変わるのは楽天へ送る販売可能数量（0）だけです。
ローカルのPostgreSQLで `inv_sale_reserve()` を実行し、`rental_available 1 → 0`・
`sale_listed` は `true` のまま・`sale_qty 1 → 0` になることを確認しています。

**同時に来たときは片方だけ成功します。** 「在庫1台・`rental_eligible=true`」の同じ個体に、
楽天の販売予約（`inv_sale_reserve`）と8ECのレンタル申込（`inv_rental_request`）を
別接続から同時に投げるテストを20回行い、**毎回どちらか一方だけが確保**（販売16・レンタル4）、
両方成功・両方失敗ともに0件でした。負けたほうは待たされずに
「あいにく、この商品はいまレンタルできる台数がありません」で返ります
（`inv_reserve_available_item()` の `for update skip locked` による）。

公開条件は `kind='individual'` かつ `rental_enabled = true`（楽天に出品中かどうかは条件にしない）。
シリアル・仕入価格・販売予定価格・利用者・備考・保管場所はビューに含めません。
トップが閲覧されるたびに楽天APIを呼ぶことはなく、保存済みの商品データだけを読みます。
画像URLが壊れていれば次の候補に切り替え、最後は「画像準備中」の枠にします（無限再読込はしない）。

### 商品写真は楽天から取り込む（手入力が前提ではありません）

楽天に出品している商品の写真は、**楽天APIから取り込んで商品マスターに保存**します。
8ECのページを開くたびに楽天APIを呼ぶことはしません（公開ページは商品マスターだけを読みます）。

```
inventory_channel_listings（channel='rakuten' の itemCode / 掲載URL）
        ↓  Edge Function rakuten-product-sync（/zaiko の「楽天商品を同期」）
     楽天API（自社 shopCode の商品だけ）
        ↓  取得した商品画像URL
inventory_products.images   ← image_url（人が指定したメイン画像）は触らない
        ↓
inv_public_catalog → 8ec.jp
```

**画像は元サイズで保存します。** 楽天APIが返す画像URLには縮小指定
（`?_ex=128x128`）が付いていて、そのまま保存すると商品詳細で大きく出したときに粗く見えます。
同期時に `_ex` を外して、店舗がアップロードした元サイズのURLを `images` に保存します
（`_ex` 以外のクエリは残します）。すでに取り込んだぶんは migration が同じ規則で直します。

**表示は代表画像の1枚だけ**です。商品マスターには複数枚保存して構いませんが、
カードも商品詳細もサムネイルを並べず1枚だけ出します（読めなければ次の候補に差し替え）。
**元画像より大きくは引き伸ばしません**（`object-fit: contain` ＋ 枠と自然サイズの小さいほうを上限にする）。
小さい写真は等倍のまま中央に置くので、拡大でぼやけることがありません。

表示に使う代表画像の優先順位（`assets/catalog.js`）：

| 順 | 取得元 |
|---|---|
| 1 | `rental_image_url`（8RENT用に指定したメイン画像） |
| 2 | `rental_images[0]`（8RENT用の画像一覧の1枚目） |
| 3 | `image_url`（`/zaiko` で人が指定したメイン画像） |
| 4 | `images[0]`（楽天同期などで入った画像） |
| 5 | 「画像準備中」 |

**`/zaiko` の「楽天商品を同期」から選べる範囲**

| 範囲 | すること |
|---|---|
| 画像が未取得の商品だけ（既定） | 楽天に掲載していて、まだ写真が1枚も無い商品だけを同期 |
| 楽天に掲載している商品すべて | 掲載中の全商品を見直す（入っている値は上書きしない） |
| 1商品だけ（掲載URLを指定） | 1件だけ試す・接続確認。反映先の商品コードも指定できる |
| 商品一覧から商品マスターを補完 | 従来どおり、型番などで照合して不足情報を埋める（該当が無ければ新規登録） |

**同期が終わったあとの画面**

- 上部に **「楽天商品との同期が完了しました」** が出て、右下のボタンは **`✓ 同期完了`** になり押せなくなります
  （同じ同期を続けて叩かないため）
- 「写真が無い◯商品」の件数は**その場で取り直して**最新にします（範囲の選択肢の件数も同時に直します）
- 失敗があれば **理由ごとにまとめて**、商品ごとに原因と直しかたを出します
- **「失敗した◯商品のみ再試行」** を押すと、その商品コードだけを Edge Function に渡してやり直します。
  **成功したぶんは対象にしないので、全件の再同期は要りません**

| 失敗の理由 | 意味 | 直しかた |
|---|---|---|
| 楽天APIで商品が見つからない | `external_item_code` はあるが、その商品コードが自社店舗の一覧に無い | 出品終了か商品コードが古い。楽天側をご確認ください |
| listing URL不一致 | 登録してある掲載URLの商品が楽天側に無い | 商品詳細の「楽天」行でURLを直す（同期が返す更新候補も使えます） |
| external_item_code不明 | 商品コードも掲載URLも無く、照合の手がかりが無い | 商品詳細の「楽天」行にURLを入れる |
| APIレスポンスに画像なし | 楽天では見つかったが、APIが画像を返さなかった | 楽天の商品ページに画像が登録されているか確認 |
| APIエラー | 取り込み中にエラーが返った | 時間をおいて再試行 |
| 未確認のページが残っています | 商品一覧を最後まで見きれなかった（時間切れ） | 再試行すると続きから探します |

**同期の対象になるのは「商品単位の楽天listing」がある商品です**

中古は実物1台ごとに出品するので、出品情報は個体別（`inventory_channels`）に入ります。
ところが**同じ商品ページに2台以上をぶら下げている**と、商品単位
（`inventory_channel_listings`）に楽天の行が無いままになり、画像同期の対象から漏れます。

> 例：`P-00536 / PROBOOK445G11` は個体 `00039769953` と `00039770113` が同じ楽天URLを共有。
> 商品単位の楽天listingが無く、楽天に出ているのに画像が入りませんでした。

`zaiko/migrations/2026-09-19-listings-from-items.sql` が、同じ状況の商品をまとめて埋めます。

| | 動き |
|---|---|
| まとめる条件 | 同じ商品で**同じURL・同じSKU**の個体だけ |
| 違う掲載が混ざっている商品 | **自動で作らず「要確認」に出す**（どれが正しい掲載かは人が決める） |
| すでに商品単位の楽天listingがある商品 | 作らない（重複させない） |
| 引き継ぐ値 | `url` / `state` / `sku` と、`price` は **`inventory_channels.price`（モールでの販売価格）**。自社の販売予定価格（`inventory_items.plan_price`）は別概念なので使いません |
| `external_item_code` | URL・SKUから推測しない（空のまま）。次の楽天API同期でAPIが返す正式値を保存 |
| `inventory_channels` | 消さない |

何度実行しても安全です（2回目以降は0件）。要確認の商品は migration の末尾の確認クエリで一覧できます。

あとから増えた商品は、`/zaiko` の商品詳細「販売情報」タブに出る**「個体から作る」**ボタン
（`inv_listing_from_items()`）で1商品ずつ同じ補完ができます。

**商品の見つけ方（itemCodeはURLから推測しません）**

楽天の `itemCode` は `店舗コード:商品ID` の形ですが、**掲載URLの末尾とは一致しません**
（例：`…/8commerce/k08137507-196-1/` の正式な itemCode は `8commerce:10000120`）。
そのため、URLから itemCode を組み立てることは一切せず、APIが返す正式な値だけを使います。

| 商品の状態 | 探し方 |
|---|---|
| `external_item_code` がある | その itemCode で直接照合（1回のAPI呼び出し） |
| 掲載URLしか無い | 自社店舗の商品一覧をページングし、APIが返す `itemUrl` と突き合わせる。見つかったらAPIが返した**正式な itemCode を `inventory_channel_listings.external_item_code` に保存**するので、次回からは直接照合になる |

ページングは **レスポンスの `pageCount` に従って最後のページまで**見ます
（`hits` は最大30、`page` は最大100＝最大3000件。安全のため100ページで頭打ち）。
固定ページ数で打ち切らないのは、後ろのページにある商品が「見つからない」ことになるためです
（`P-00537` が150件＝5ページ打ち切りで見つからなかった例）。1リクエスト/秒・429は自動リトライ、
実行時間が長くなるときは途中で区切って `next_page` を返し、画面が自動で続きから再開します。
**全ページ（最大100ページ）を確認しても見つからないときだけ**「楽天API検索対象外」として扱います。

Edge Function のログには `total_count` / `page_count` / `scanned_pages` /
`matched_by`（itemCode か url）/ `external_item_code_saved` / `url_mismatch` を出します。

**掲載URLが古い・間違っているときの検知**

モール側で商品ページのURLが変わることがあります。保存してあるURLが古いままだと、
`itemCode` が分かるまでAPIで商品を見つけられません
（実例：`P-00537` は保存 `…/8commerce/l09150188/`、実際 `…/8commerce/00039769233/`）。

そこで同期が成功したときは、**APIが返した正式な `itemUrl` と保存済みURLを毎回見比べます**。

| 保存済みURL | どうなるか |
|---|---|
| 空 | 正式URLをそのまま保存 |
| 正式URLと同じ（http/https・末尾スラッシュ・クエリの違いは無視） | `url_checked_at` を更新するだけ |
| 正式URLと違う | **自動では書き換えず** `inventory_channel_listings.url_candidate` に更新候補として入れ、履歴に「掲載URL差異」を残す |

更新候補は `/zaiko` の同期結果と、商品詳細の「販売情報」タブに出ます。
「URLを更新」（`inv_listing_url_accept()`）で差し替え、「このまま」（`inv_listing_url_dismiss()`）で
候補だけ消します（次の同期でまた差があれば、また知らせます）。URLは人が入れた値でもあるので、
同期が黙って書き換えることはしません。

API呼び出し回数は「商品数」ではなく「ページ数」です。結果は

```
画像取得成功 ○件 ／ 商品情報更新 ○件 ／ 失敗 ○件
```

で表示し、楽天側で見つからなかった商品（掲載URL・itemCodeの誤り、出品停止など）も一覧で出します。

取り込むのは**自社店舗（`RAKUTEN_SHOP_CODE`）の商品だけ**です。他店が撮影した写真は対象外なので、
下の「商品画像」で書いている著作権の問題は起きません。

手で入れることもできます。`/zaiko` の商品詳細「商品画像を登録・変更」（`inv_product_images_set`）で
メイン画像（`image_url`）と画像一覧（`images`）を入れます。公開ページは次の読み込みから反映され、
再デプロイは要りません。**楽天同期は `images` にだけ書き込み、人が指定したメイン画像は上書きしません。**

PACK・Supported Plan などの固定料金は承認済みのサービス料金として HTML に書いており、
商品ごとの月額・販売価格（すべて DB 由来）とは分けています。

`#contact`（申込・相談）は、サイト内の他ページからの `/#contact` の着地点でもあります。
送信先はこれまでどおり `/api/contact`（Slack通知・Supabase保存）で、`source` は `top` です。

> **公開前に必要な /zaiko 側の準備**
> トップに商品が並ぶ条件は `rental_enabled = true` です。2026-09-18 時点の本番データでは
> `rental_enabled` の商品が0件（`inv_rental_catalog` が空）、商品画像も未登録のため、
> このままでは商品セクションが「準備中」の表示になります。`/zaiko` の商品詳細で
> **「8RENT設定を変える」→ 公開する** と、**「商品画像を登録・変更」**（または楽天同期）を
> 行ってください。どちらも再デプロイなしで次の読み込みから反映されます。

### 申込から発送・返却まで

```
/zaiko で仕入れる → rental_enabled をオンにする → トップ（8RENT）に公開 → 申込 → 発送 → 返却
```

### データの基準は/zaiko

`/zaiko` の商品マスタ（`inventory_products`）にレンタル向けの列を足しただけで、
在庫を別に持ちません。**個体の状態がそのままレンタル可否になります。**

| 個体の状態 | レンタル可能数への影響 |
|---|---|
| 在庫（かつ8RENT対象） | 数える（＝レンタル可能） |
| 在庫（8RENT対象外） | 数えない（販売用にとってある1台） |
| 予約中 | 数えない（8ECから申込が入り、発送待ち） |
| 貸出中 | 数えない（社内の内部貸出と同じ状態を共用する） |
| 販売予約 | 数えない（楽天など販売チャネルで受注が入り、発送待ち） |
| 修理中・故障・紛失・廃棄・売却済 | 数えない |

**レンタル可能数 = `status='在庫'` かつ `rental_eligible=true` の個体数。**
貸出中・予約中・販売予約・修理中などは「在庫」ではないので自然に外れます。
販売（楽天）とは同じ実在庫を共有し、先に確保したほうにその1台が割り当たります
（`inv_reserve_available_item()`）。レンタルできるのは
**商品が `rental_enabled = true`（掲載ON）かつ 8RENT対象の在庫が1台以上あるとき**だけです。

### 8RENTに出す個体を選ぶ（同じ商品10台のうち3台だけレンタル）

「8RENTに出す」は商品単位ではなく**実物1台ずつ**の設定です。

| 設定 | 持ち場所 | 意味 |
|---|---|---|
| 掲載 `rental_enabled` | `inventory_products` | その商品を8EC（トップ＝8RENT）に載せるか |
| レンタル対象 `rental_eligible` | `inventory_items` | この1台をレンタルに回すか（既定は false） |

たとえば ProBook 450 G9 が10台あるなら、3台だけ8RENT用にして残り7台は販売優先、
という運用ができます。楽天の受注（`inv_sale_reserve()`）は**レンタル対象に選んでいない個体から
先に**確保するので、8RENT用に確保した台数は最後まで残ります。

在庫のうちは、レンタル対象の個体も楽天で売れます（同じ1台を二重には確保しません）。

**商品の掲載（`rental_enabled`）の扱い**

| きっかけ | どうなるか |
|---|---|
| 最初の1台を8RENT対象にした | 商品が非掲載なら**自動で掲載ON**（非掲載のままだと8ECに出ないため） |
| レンタル対象が0台になった | **自動ではOFFにしない。** 8ECでは「在庫切れ」になり申込はできません |

自動でOFFにしないのは、`rental_enabled` がもともと「人が商品詳細で切り替える掲載設定」だからです
（値を変えるのは `inv_product_rental_set()` だけ、という既存の決めかたをそのままにしています）。
一時的に対象が0台になっただけで掲載が消えると、写真・説明・月額まで設定し直すことになり、
「掲載は維持・数量だけ0」という楽天側の扱いともそろわなくなります。
0台になった商品は一括操作の結果画面で知らせるので、止めるときは人が商品詳細から非公開にします。

```
rental_eligible=true の1台
  ├─ 8ECで申込   → 予約中     → 楽天へ送る販売可能数量から外れる
  └─ 楽天で受注  → 販売予約   → 8ECのレンタル可能数から外れる
```

個体は `/zaiko` の在庫一覧（個体別）でチェックして「8RENTに出す」でまとめて選びます
（→「在庫一覧からまとめて操作する」）。1台だけなら個体詳細の「操作」からも切り替えられます。

### 商品マスタに足した列

| 列 | 意味 |
|---|---|
| `rental_enabled` | true の商品だけが8EC（トップ・8RENT）に掲載される（実際に貸せるかは個体の `rental_eligible` と在庫しだい） |
| `rental_price_month` | 月額料金 |
| `rental_min_months` | 最低利用期間（月） |
| `office_supported` | Office対応 |
| `trial_eligible` | お試し対象 |
| `rental_tags` | おすすめ表示（`recommend` / `popular` / `new`） |
| `rental_description` / `rental_image_url` / `rental_images` | 8RENT公開用の説明文・画像 |

`/zaiko` の商品詳細（基本情報タブ）に「8RENT設定を変える」があり、ここで全部まとめて入れます。
公開・非公開が変わったときだけ履歴に残ります（`inv_product_rental_set`）。

### 申込から返却までの一連

申込は `inventory_rental_requests` に入ります。個体の割り当ては申込と同じトランザクションで
自動的に行われるので、**ほぼ同時の2件の申込で同じ1台が二重に割り当たることはありません**
（`for update skip locked` で行ロックを取る）。

```
8RENT公開ページで申込
  ↓ inv_rental_request()（anonが実行できる唯一の書き込み経路）
  在庫の個体を1台、その場で「予約中」にする
  ↓ /zaiko の「8RENT申込」画面で確認
発送する → 個体が「貸出中」に（inv_rental_set_status）
  ↓
返却済みにする → 個体が「在庫」に戻る
```

キャンセルも同じ関数で扱い、個体は「在庫」に戻ります。すべて履歴に残ります。

### 公開ページが読む・書く経路

anon（8RENTの一般訪問者）には以下だけを許可し、テーブルへの直接権限は与えません。

| 経路 | 中身 |
|---|---|
| `inv_public_catalog`（ビュー・select） | 公開用の列だけ。仕入価格・原価などの内部情報は含まない（`inv_rental_catalog` も残しているが、公開ページは共通の `inv_public_catalog` を読む） |
| `inv_rental_request()`（RPC） | レンタル申込。実行だけを許可し、テーブルへの直接書き込みは許可しない |

### 旧レンタル機能は削除済み

以前 `/admin/rental/` で独自に管理していた `rental_items` / `rental_orders`
（/zaiko とは別の在庫を持つ仕組みだった）は、**この8RENTに完全に置き換えて削除しました。**
`/admin/rental/index.html` と `rental/supabase-setup.sql` はリポジトリから削除し、
`zaiko/setup.sql` の実行時に `rental_items` / `rental_orders` テーブルと
`rental_public_inquiry()` 関数も削除されます（**元に戻せません**）。

`zimu_is_admin()` は棚卸・決算資料・商品画像など `/admin/` の他の画面でも使う
共有の関数なので、これは削除していません。

在庫は `inventory_products` ＋ 個体（`inventory_items`）＋
`inventory_rental_requests`（8RENTの申込）の3つだけを基準にしています。

## EC一元管理（/admin/ec/）

8EC を商品・在庫のマスターにして、楽天・Amazon・Yahoo! への出品をまとめて扱う画面です。

### 中古（`/admin/`）との住み分け

いま動いている `/admin/` の EC在庫管理は、オークションで仕入れた**中古品を1台ずつ**扱う仕組みです
（1行＝現物1台。棚卸・決算資料・ショップ出品がこれに乗っています）。
一方このモール一元管理は、**同じ型番を何台も持つ新品SKU**が前提で、
「在庫10台 → 楽天で1台売れる → 9台」と数が減る必要があります。

この2つは数え方が根本的に違うので、**表を分けて併存**させています。
`/admin/ec/` は `ec_products` を、`/admin/` は従来どおり `ec_items` を使い、互いに影響しません。

| | `/admin/`（中古） | `/admin/ec/`（新品SKU） |
|---|---|---|
| 1行の意味 | 現物1台 | 1SKU（同じ型番を何台でも） |
| 在庫 | 売れたら「販売済み」になる | 数量が減る |
| 表 | `ec_items` | `ec_products` / `ec_listings` |

### セットアップ

Supabase の SQL Editor で `admin/ec-master-setup.sql` を実行します。何度実行しても安全です。
既存の `ec_items` には触れないので、棚卸・決算資料はそのまま動きます。

作られるもの：

| 表・関数 | 役割 |
|---|---|
| `ec_products` | 商品マスター。SKU・価格・在庫・スペック・中古PC向け項目 |
| `ec_listings` | SKU×モールの出品設定（出す/出さない・モール別の商品名と価格・出品状態） |
| `ec_stock_moves` | 在庫の増減履歴（いつ・どのモールで・いくつ・なぜ） |
| `ec_sync_log` | モール連携の実行履歴 |
| `ec_stock_apply()` | 在庫を増減する関数 |

### 在庫は必ず `ec_stock_apply()` を通す

在庫は複数のモールから同時に減りえます。画面側で「読んで、引いて、書き戻す」をやると、
ほぼ同時の2件で片方の減少が消えます。`ec_stock_apply()` は
`update ... returning` で1文にまとめて行ロックを取り、履歴を同じトランザクションで残します。
マイナス在庫になる場合は例外を投げて、増減ごとなかったことにします。

> 3セッションから同時に150回引く検証で、在庫100に対して成功100・失敗50、
> 残0・履歴100行・`stock_after` が100通り（＝取りこぼしなし）を確認しています。

### モールを増やすとき

モールごとの違いは `admin/ec/connectors.js` だけに閉じ込めてあります。
画面側はモール名を知らずに動くので、**コネクタを1つ足せば増やせます**。

```js
var NEWMALL = {
  key:'newmall', label:'新しいモール', short:'新', color:'#333', phase:2,
  csv:{ encoding:'shift_jis', sep:',', filename:(ymd)=>'newmall-'+ymd+'.csv',
        columns:[ {h:'商品コード', v:(p,l)=>p.sku}, ... ],   // 出力する列
        keyField:['商品コード'],                              // 取込のキー列
        fields:{ price:{h:['価格'], t:num, to:'listing.price'} } },
  api:null
};
```

### CSVの列名について

モールのCSVテンプレートは契約プランや店舗によって列が増減します。
`connectors.js` に書いてあるのは主要列で、**そのまま通る保証はありません**。
画面の「ヘッダー照合」に実物のテンプレートを読ませると、
食い違っている列（出力側の余分／取込側の不足）を出すので、最初の1回はそれで確かめてください。

文字コードは楽天・Yahoo!を Shift_JIS、Amazon・8EC を UTF-8 として出力します（画面で切り替え可）。
ブラウザは Shift_JIS を読めても書けないため、出力用の変換表だけ自前で持っています。

```bash
python3 tools/build-cp932.py   # admin/ec/cp932.js を作り直す（手で編集しない）
```

取り込み側は `TextDecoder` に任せるので変換表を使わず、Shift_JIS / UTF-8 を自動で見分けます。

| 4 | `rental/supabase-setup.sql` | レンタル機材 |
| 5 | `admin/setup-all.sql` | 棚卸・決算資料（請求日／入金日）・商品画像管理 |

### Edge Function（Stripe 決済リンクの自動生成）

管理画面の「ショップ出品」タブで決済リンクをボタン1つで発行するために、
Stripe の Products / Prices / Payment Links API を呼ぶ Edge Function をデプロイします。

```bash
# 管理者だけが叩く関数なので --no-verify-jwt は付けない
supabase functions deploy create-payment-link

# 公開ショップから呼ぶ動的チェックアウト（こちらは匿名アクセスのため --no-verify-jwt）
supabase functions deploy create-checkout --no-verify-jwt
```

デプロイ後、Supabase ダッシュボード → Edge Functions → 各関数の **Secrets** に設定します。

| Secret | 用途 |
|---|---|
| `STRIPE_SECRET_KEY` | Stripe のシークレットキー（`sk_live_…` / テストは `sk_test_…`） |
| `SHOP_URL` | 任意。決済完了後の戻り先。既定は `https://www.8ec.jp/shop/` |

> `create-payment-link` は呼び出し元が管理者（`zimu@8grp.co.jp`）かを JWT で検証し、
> 価格は必ずサーバー側で DB から読み直します（金額をブラウザに信頼させません）。

## 問い合わせフォームと Slack 通知（Vercel 側の設定）

各ページのフォームは **`/api/contact`（Vercel のサーバーレス関数）** に送信され、
そこで Supabase への保存と Slack への通知をまとめて行います（`api/contact.js`）。

### Vercel の環境変数

プロジェクト → **Settings → Environment Variables** で設定します。
変更後は再デプロイすると反映されます。

| 変数名 | 必須 | 内容 |
|---|:--:|---|
| `SLACK_WEBHOOK_URL` | 任意 | Slack の受信 Webhook（`https://hooks.slack.com/services/...`）。**未設定でもフォームは動作します**（Slack 通知だけスキップ） |
| `SUPABASE_URL` | 任意 | 既定値がコードに入っているため通常は不要 |
| `SUPABASE_ANON_KEY` | 任意 | 同上（RLS で保護された公開鍵） |
| `ADMIN_CONTACT_URL` | 任意 | Slack 通知のボタンの遷移先。既定 `https://www.8ec.jp/admin/contact/` |

### Slack の受信 Webhook を作る

1. <https://api.slack.com/apps> → 「Create New App」→「From scratch」
2. アプリ名（例：8ec お問い合わせ通知）と通知先ワークスペースを選ぶ
3. 左メニュー「Incoming Webhooks」を On にする
4. 「Add New Webhook to Workspace」→ 通知したいチャンネルを選んで許可
5. 表示された URL を、Vercel の `SLACK_WEBHOOK_URL` に貼る

Webhook URL は **サーバー側の環境変数としてのみ参照** し、ブラウザに配信されるコードには
一切含めません（含めると URL を知った第三者が自由にチャンネルへ投稿できてしまうため）。

Slack 通知に失敗しても、お客様のフォーム送信は成功として扱います
（Slack 側の障害や URL 未設定で問い合わせを取りこぼさないため）。
